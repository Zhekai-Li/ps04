Abstract
Combinatorial optimization (CO) underpins decision-making across science, engineering and industry, especially manufacturing, logistics, healthcare operations and energy management. However, designing effective heuristics for each new problem variant requires deep domain knowledge and months of expert iteration. Directly prompting large language models (LLMs) can generate executable code, but single-pass synthesis of complete heuristics routinely fails on new CO problems. Here we introduce LLM-driven Algorithm Construction via Complementary Evolution (LACE), a framework that decomposes algorithm design into an input schema, output schema, tool library and heuristic portfolio (the \({\mathcal{I}}\)–\({\mathcal{O}}\)\({\mathcal{T}}\)\({\mathcal{H}}\) interface) and refines the portfolio through time-constrained complementary evolution. The interface specifies a verified problem contract under which the LLM operates, directing model capacity to high-level algorithmic reasoning rather than problem-specific implementation. Complementary evolution then iteratively generates and selects specialist heuristics capable of solving heterogeneous instances within strict runtime budgets. Across 36 classical CO-Bench problems, LACE attains an average score of 0.945, against 0.870 for the strongest existing LLM-based method and 0.571 for direct LLM prompting without any framework, locating the gain in the framework rather than the model. On four structurally new problems, LACE reaches 0.97–0.99, while five existing LLM-based baselines fail to produce any feasible algorithm. These results demonstrate that effective algorithm discovery for such problems can be automated to a substantial degree.

Main
Artificial intelligence (AI) has rapidly expanded its scientific and technological reach, transforming domains from molecular biology1,2 and mathematical reasoning3,4 to reinforcement learning algorithm discovery5 and scientific prediction6. Yet these advances have not extended to automated algorithm design for combinatorial optimization (CO), in which discrete search spaces resist end-to-end learning or gradient-based approaches. This gap is consequential, as real-world systems in global logistics, manufacturing, healthcare operations and energy management rely on solving CO problems7,8,9,10. These problems typically exhibit exponentially growing search spaces, rendering exact solution methods computationally intractable11. This inherent complexity has driven the widespread adoption of heuristic algorithms, which provide approximate solutions within feasible timeframes12. However, deploying heuristics faces three compounding challenges: the structural diversity of CO problems precludes universal algorithms; effective heuristics must be manually crafted by domain experts through time-intensive iteration13; and the landscape of CO problems continuously expands through new variants and formulations14,15,16,17,18. These challenges create a pressing need for approaches that can automatically generate high-quality heuristics, without months of manual design effort per problem.
Large language models (LLMs) offer an intriguing opportunity in this direction17,19. Recent works demonstrate that LLMs can generate executable code20 and construct heuristics through iterative refinement and evolutionary search21,22,23,24,25. More recent agentic systems coordinate multiple LLM roles to translate a natural-language problem description into executable solvers26,27,28. However, existing LLM-based approaches exhibit a consistent structural limitation: most prompt LLMs to synthesize complete heuristics in a single pass4,21,22,29. Although effective for classical benchmarks with well-established patterns in pretraining corpora, this paradigm fails on structurally new CO problems, producing infeasible, non-executable or computationally intractable heuristics23,25. Two fundamental barriers underlie this limitation. First, synthesizing complete heuristics for unfamiliar constraint structures may exceed the compositional reasoning capacity of LLMs. Second, existing approaches do not guarantee that generated heuristics will meet practical runtime constraints during execution. These barriers raise two questions: (Q1) Generalization: What interface enables LLMs to generate heuristics that generalize robustly across structurally diverse CO problems, including problems unlikely to be well represented in their training corpora? (Q2) Efficiency: How can LLM-based heuristic generation systematically satisfy varying real-world runtime constraints, producing solutions that span the quality–time trade-off spectrum from emergency decisions to strategic planning?
We introduce LLM-driven Algorithm Construction via Complementary Evolution (LACE), a framework (Fig. 1) that addresses Q1 and Q2 through two synergistic mechanisms: universal modular decomposition and time-constrained complementary evolution. For generalization, LACE decomposes algorithm design into four modules—input schema \({\mathcal{I}}\), output schema \({\mathcal{O}}\), tool library \({\mathcal{T}}\) and heuristic portfolio \({\mathcal{H}}\)—providing a unified \({\mathcal{I}}\)–\({\mathcal{O}}\)–\({\mathcal{T}}\)–\({\mathcal{H}}\) interface for automated heuristic generation across diverse CO problems. The problem contract (\({\mathcal{I}}\), \({\mathcal{O}}\), \({\mathcal{T}}\)) is constructed automatically by an LLM agent from a natural-language problem statement, without per-problem human authoring; \({\mathcal{H}}\) is then generated by the LLM given this contract, focusing exclusively on algorithmic reasoning without mastering low-level implementation details for each new problem. For efficiency, LACE employs time-constrained complementary evolution to refine \({\mathcal{H}}\) through seven operators—five generation operators and two reactive repair operators—producing the complementary heuristic portfolios that give the method its name, by means of rank-aware selection that ensures each instance is covered by at least one specialist; by executing this process independently under multiple runtime budgets, LACE spans the quality–time trade-off from emergency decisions to strategic planning. We evaluate LACE on 40 CO problems spanning six families, consistently outperforming classical solvers and existing LLM-based approaches, and generalizing zero-shot to four structurally new problems where direct LLM synthesis fails entirely. These results demonstrate that automated heuristic discovery for new CO problems, traditionally a months-long expert effort, can be replaced by an automated procedure driven by a natural-language description alone.
Results
LACE overview
LACE operates through a two-stage architecture. Stage one employs universal modular decomposition to enable cross-problem generalization by decomposing algorithm design into four modules (\({\mathcal{I}}\)–\(\mathcal O\)–\(\mathcal T\)–\(\mathcal H\)), allowing LLMs to generate heuristics without constructing complete solvers for each problem. Stage two ensures computational efficiency through time-constrained complementary evolution, producing heuristic portfolios that span the quality–time trade-off spectrum and satisfy varying runtime constraints.
Stage one: universal modular decomposition
To achieve generalization across structurally diverse CO problems, LACE decomposes algorithm design into four modules: an input designer, which defines the input schema \({\mathcal{I}}\) describing problem input data; an output designer, which defines the output schema \({\mathcal{O}}\) describing the required solution output structure; a tool designer, which encapsulates complex domain logic into a callable tool library \({\mathcal{T}}=\{{\tau }_{1},\ldots ,{\tau }_{K}\}\) containing a feasibility checker, an objective evaluator and problem-specific helpers; and a heuristic generator, which produces an initial portfolio \({{\mathcal{H}}}_{0}\) in which each heuristic is a self-contained solve function \(h:{\mathcal{I}}\to {\mathcal{O}}\) taking an input from \({\mathcal{I}}\) and returning a feasible output in \({\mathcal{O}}\). Each heuristic invokes tools from \({\mathcal{T}}\) to internally construct a feasible solution. Crucially, this separation of the problem contract (encoded in \({\mathcal{I}}\), \({\mathcal{O}}\), \({\mathcal{T}}\)) from algorithmic reasoning (encoded in \({\mathcal{H}}\)) enables LLMs to focus on high-level decision-making without mastering low-level implementation details for each new problem (see Methods for full specifications).
Stage two: time-constrained complementary evolution
Stage two refines \({{\mathcal{H}}}_{0}\) into a final complementary portfolio \({{\mathcal{H}}}^{* }\) explicitly optimized for heterogeneous instances under strict runtime constraints Tmax. The evolution process iteratively applies five generation operators—local refinement (LR), reflective redesign (RR), complementary crossover (CC), comparative synthesis (CS) and diversity injection (DI)—to generate candidate heuristics that target distinct limitations of the current portfolio. These are complemented by two reactive repair operators—error repair (ER) and efficiency improvement (EI)—which are triggered automatically when candidates fail execution or exceed the runtime budget. Generated candidates combine with the current portfolio to form a pool of 2n heuristics, from which n are retained by way of a ranking-based complementary selection objective that minimizes the average best rank across all instances, ensuring balanced coverage regardless of instance scale. To accommodate diverse operational requirements, stage two is executed independently under multiple time budget settings, producing portfolios that span the quality–time trade-off spectrum from emergency decisions to strategic planning (see Methods for operator definitions and selection formulation).
Performance on classical benchmarks
We evaluate LACE on CO-Bench30, a third-party benchmark of 36 CO problems, which we group into five problem families: scheduling; routing and graphs; packing and cutting; location and assignment; and selection and knapsack. Methods are scored under CO-Bench’s protocol on three metrics—Avg Score (a primal-gap-style normalized quality score), Valid Rate (the fraction of problems on which the generated heuristic algorithm yields feasible solutions on every test instance) and Survival Rate (the fraction of test instances reaching at least 99% of the best-known objective)—with all LLM-based methods sharing OpenAI o3 Mini as the backbone for fair comparison.
LACE leads on all three metrics (Fig. 2a). Valid Rate score for LACE reaches 0.944, whereas no other LLM-based baselines exceed 0.611. This means that these methods produce infeasible solutions on at least one test instance for nearly 40% of CO-Bench problems, whereas LACE delivers heuristic algorithms with full feasibility on essentially every problem. Avg Score for LACE reaches 0.945, exceeding the strongest LLM-based baseline (0.870) and the classical solver suite (0.797); the bare-LLM baseline, in which OpenAI o3 Mini is prompted to produce a heuristic algorithm directly without any framework, achieves only 0.571, demonstrating that the gains stem from the \({\mathcal{I}}\)\({\mathcal{O}}\)\({\mathcal{T}}\)\({\mathcal{H}}\) decomposition and complementary evolution rather than the LLM backbone alone. Survival Rate for LACE reaches 0.623, more than 17 percentage points above any previous baseline, indicating that the majority of test instances are solved to near-optimality. The advantage holds within every family (Fig. 2b): LACE attains the highest Avg Score in all five. The same modular interface, generated automatically from each problem’s natural-language description without per-problem authoring, supports heuristic discovery across structurally diverse CO problems.
Zero-shot generalization to new problems
A stronger test of generalization is whether LACE can synthesize effective heuristics for problems that are, to the best of our knowledge, newly formulated and therefore unlikely to be well represented in LLM training corpora. We design four such problems centred on container-terminal logistics: a port scheduling problem (PSP) and three tugboat-routing variants (TRS, MB-TRS and TRS-VS) introducing multi-depot dispatch and speed-dependent fuel coupling.
Across the four problems (Fig. 3a–d), LACE attains Avg Scores of 0.981, 0.990, 0.978 and 0.969. Gurobi reaches 0.53 within 1 min and 0.64 within 30 min, as its integer formulations do not converge to global optima at the tested sizes. Six tuned metaheuristics range from 0.72 to 0.96 on the first three problems and degrade to 0.54–0.58 on TRS-VS, where the increased problem complexity leads to substantially worse performance. Under the same OpenAI o3 Mini backbone, five LLM-based methods (FunSearch, EoH, EoH-S, Greedy Refine and ReEvo) produce no feasible algorithm on any of the four problems; HeurAgenix returns feasible but substantially weaker solutions than LACE (0.23–0.58). These results demonstrate that LACE’s modular decomposition enables zero-shot generalization to structurally new problems, a capability that existing LLM-based methods fail to achieve.
Contributions of tool library and portfolio
LACE derives its effectiveness from two structural mechanisms: the tool library \({\mathcal{T}}=\{{\tau }_{1},{\tau }_{2},\ldots ,{\tau }_{K}\}\), which provides the LLM with reusable building blocks for heuristic construction, and the heuristic portfolio of size n, which combines specialized algorithms across the instance space. We quantify the contribution of each.
Tools are essential for reliable heuristic construction (Fig. 4a). With no tools available (K = 0), 11–35% of generated heuristics fail to produce a usable algorithm across the six problem families, with the highest failure rate on the four new CO problems whose constraint structures are unlikely to be well represented in LLM training corpora. Tools therefore play a substantial role in turning LLM-generated heuristics into executable algorithms, by exposing validated operations that would otherwise have to be re-derived from scratch for each new problem. The complementary portfolio is similarly essential (Fig. 4b). A single best heuristic (n = 1) achieves Avg Score 0.80–0.88 across families. Increasing n yields monotone improvement across all six families, reaching 0.90–0.99 at n = 10. This persistent improvement is consistent with the role of the portfolio as a set of specialists that jointly cover the instance space, in which each additional heuristic contributes to coverage of instances that earlier members handle less well. Together, these results confirm that both the tool library and the complementary portfolio are indispensable components of LACE: tools ensure reliable heuristic construction and portfolio diversity ensures broad coverage across heterogeneous instances. Additional ablations isolating the complementary selection rule, the evolution operators, the per-instance runtime budget Tmax and the number of evolution iterations Nmax are reported in Supplementary Note 5 and Supplementary Figs. 4–7.
Performance and cost across LLM backbones
We evaluate LACE under four frontier LLM backbones spanning providers and price points: DeepSeek V4 Pro, Claude Sonnet 4.6, OpenAI o3 Mini and Gemini 3 Flash Preview. All four backbones run to completion on the 40-problem benchmark with no framework-level failures and produce usable portfolios on most problems. Avg Score ranges from 0.81 to 0.98 across backbones, tracking backbone capability while the framework itself remains stable under all tested LLMs (Fig. 5a).
Per-problem averages span 3.0–7.3M tokens, US$1.6–US$45.1 in application programming interface (API) charges and 48–68 min of wall-clock time, with Gemini 3 Flash Preview offering the most favourable trade-off between solution quality and monetary cost (Avg Score 0.95 at US$1.59 per problem, roughly 28 times cheaper than Claude Sonnet 4.6). The wall-clock breakdown (Fig. 5b) shows that evaluation of generated heuristics dominates total time across all backbones, while LLM generation, repair and portfolio selection together occupy a smaller fraction. These results confirm that LACE is robust across frontier LLM backbones and that wall-clock time is governed primarily by evaluation throughput rather than LLM inference, offering a clear optimization target for reducing end-to-end runtime in future deployment.
Discussion
Our results indicate that in LLM-based heuristic discovery for CO, generalization and reliability are governed by interface design rather than by backbone scale. On the same OpenAI o3 Mini backbone, direct LLM prompting yields an Avg Score of only 0.571 across the 36 CO-Bench problems, whereas LACE, routing the same backbone through the \({\mathcal{I}}\)–\({\mathcal{O}}\)\({\mathcal{T}}\)\({\mathcal{H}}\) interface, reaches 0.945. This 0.37-point gap, obtained without any change in model capacity, locates the source of improvement in the framework rather than in the underlying language model. The mechanism behind this gap is a deliberate division of labour: by exposing a verified problem contract \(({\mathcal{I}},{\mathcal{O}},{\mathcal{T}})\) and requiring the LLM only to author a self-contained solve function on top of it, LACE removes from the model the burden of inventing complete solvers with problem-specific input parsing, output assembly and feasibility logic; model capacity is redirected to high-level algorithmic reasoning. This perspective sits adjacent to, rather than against, the prevailing scaling-law narrative19. Scaling continues to drive backbone capability, and the Avg Score across the four frontier backbones we evaluated tracks model strength in the expected order. However, the same backbone viewed through a different interface exhibits performance equivalent to a substantial scaling step. Therefore, structured decomposition acts as a multiplicative factor on top of scaling, accessing regimes that bare prompting cannot reach with current models. The five LLM-based baselines4,21,22,29,31 that fail on every one of our four problems while LACE attains 0.97–0.99 on the same problems with the same backbone sharpen this conclusion: when the interface absorbs the burden of problem-specific structure, generalization depends less on whether the model has seen similar problems before and more on the quality of the interface through which it operates.
The reliability of this interface-level effect rests on two complementary mechanisms operating inside the interface, each addressing a distinct failure mode of LLM-generated heuristics. The first, the tool library \({\mathcal{T}}\), addresses semantic executability, the gap between syntactically plausible LLM output and code that actually runs and produces feasible solutions. Without tools (K = 0), 11–35% of generated heuristics fail to produce a usable algorithm across the six problem families, with the highest failure rate on the new problems whose constraint structures are unlikely to be well represented in pretraining corpora (Fig. 4a); the library closes this gap by injecting validated domain primitives that the LLM would otherwise have to re-derive from scratch. One choice within \({\mathcal{T}}\) is worth highlighting: the feasibility checker does not return a binary verdict but exposes the full step-by-step constraint validation process, allowing the LLM to read each constraint boundary explicitly and internalize it during heuristic design. This suggests a more general principle for LLM–symbolic system interfaces32,33: procedural feedback that reveals constraint structure is more useful than declarative pass/fail verdicts. The second mechanism, the complementary portfolio of size n, addresses instance heterogeneity. A single best heuristic (n = 1) achieves only Avg Score 0.80–0.88 across families, whereas n = 10 raises this to 0.90–0.99 with monotone improvement at every intermediate step (Fig. 4b); coverage emerges from specialist synergy rather than from a monolithic optimum. These two layers distinguish LACE from existing LLM-based heuristic-discovery methods: FunSearch4, EoH21, HeurAgenix23 and ReEvo22 evolve a single best heuristic and lack the portfolio layer; EoH-S29 maintains a heuristic set but lacks the structured tool layer. The robustness of this two-layer design is itself notable: four frontier LLMs spanning a roughly 28× cost range all yield an Avg Score above 0.81, and Fig. 5b shows that wall-clock time is dominated by heuristic evaluation rather than by LLM inference, locating the next engineering frontier on the evaluation side rather than the generation side.
Three limitations bound the current framework. First, the evaluation bottleneck identified in Fig. 5b is currently mitigated by engineering parallelism rather than by an algorithmic reduction in evaluation cost. Each candidate heuristic is evaluated across 128 development instances in parallel, and the 40 problems run independently on separate nodes; the per-instance evaluation cost itself, however, is not reduced. When instance sizes grow large enough that single-instance evaluation becomes expensive, or when deployment resources cannot support this level of parallelism, the engineering-only solution will not scale. Second, our variance characterization is incomplete: the five-seed box plots in Fig. 3 capture run-to-run variance only on the four new problems, and the joint variance structure across backbones, problem families and random seeds has not been systematically modelled, leaving the reproducibility envelope for production deployment partially undefined. Third, these results characterize LACE within the single-pass heuristic-generation regime, in which a complete solve function is synthesized offline and then executed under a fixed per-instance runtime budget; LACE does not target the iterative, long-horizon algorithm-engineering regime, in which an agent repeatedly refines a candidate solution over an extended interaction horizon, as exemplified by the ALE-Bench benchmark34 and by agentic systems targeting it28. These boundaries notwithstanding, the results already support a broader set of conclusions about practical impact and future applicability.
Taken together, these results suggest that a meaningful share of the algorithm design work traditionally requiring months of expert iteration can be largely automated. On the OpenAI o3 Mini backbone, a complete LACE run for a single new CO problem averages 59 min of wall-clock time and approximately US$9.21 in API charges; under the lowest-cost backbone we evaluated, Gemini 3 Flash Preview, the same procedure costs roughly US$1.59 per problem while still achieving Avg Score 0.95. These figures place automated heuristic discovery within the budget of individual research groups and small engineering teams rather than only large industrial laboratories. Several application domains stand to benefit directly. Container-terminal logistics is the most immediate, with the four new problems (PSP, TRS, MB-TRS and TRS-VS) reflecting operational variants that arise when a new berth layout, a new tug fleet or new fuel-price coupling enters the planning problem and conventional tuned metaheuristics must be revisited. Healthcare scheduling (surgical block assignment, bed allocation and emergency-room flow control) presents structurally similar requirements: heterogeneous instance pools, frequent constraint changes and limited algorithm-engineering capacity within individual institutions. Energy dispatch problems, in which grid topology, storage profiles and policy constraints shift faster than dedicated heuristic teams can re-tune, fit the same pattern, as does manufacturing and supply-chain redesign under new product introductions. Beyond CO, the broader pattern that LACE instantiates, namely a structured problem contract, specialist generation under LLM control and complementarity-aware selection, extends to other heterogeneous-instance search domains including formal verification and programme synthesis. In all of these, the relationship between human and machine is one of complementary specialization: humans articulate the problem in natural language, while machines construct the formal contract, generate the strategy space and select complementary specialists automatically. LACE provides a concrete and reproducible instantiation of this principle, suggesting that interface design, rather than backbone scaling alone, may be the most direct route to highly automated algorithm discovery.
Methods
LACE execution procedure
Algorithm 1 formalizes the complete LACE procedure used in all experiments. Given a problem description \({\mathcal{P}}\) (provided as a natural-language description), development instances \({\mathcal{D}}=\{{i}_{1},{i}_{2},\ldots ,{i}_{m}\}\) and time budget Tmax, the framework outputs a complementary heuristic portfolio \({{\mathcal{H}}}^{* }=\{{h}_{1},{h}_{2},\ldots ,{h}_{n}\}\) in which each \(h\in {{\mathcal{H}}}^{* }\) satisfies \({t}_{i}(h)\le {T}_{\max }\) for all \(i\in {\mathcal{D}}\). Throughout this section, ti(h) denotes the runtime of heuristic h on instance i and fi(h) denotes the corresponding objective function value (lower is better). The framework operates through two stages. Stage one constructs the four modules—input schema \({\mathcal{I}}\), output schema \({\mathcal{O}}\), tool library \({\mathcal{T}}\) and heuristic portfolio \({{\mathcal{H}}}\)—generating an initial heuristic portfolio \({{\mathcal{H}}}_{0}\) through the heuristic generator. Stage two iteratively refines this portfolio through five generation operators (LR, RR, CC, CS and DI), two reactive repair operators (ER and EI) and complementary selection. Detailed specifications of each component are provided here.

Stage one: universal modular decomposition
Stage one instantiates four modules that together constitute the \({\mathcal{I}}\)–\({\mathcal{O}}\)–\({\mathcal{T}}\)–\({\mathcal{H}}\) interface. All four modules are constructed automatically by way of dedicated LLM calls from a natural-language problem description alone, without per-problem human authoring. The problem contract (\({\mathcal{I}}\), \({\mathcal{O}}\), \({\mathcal{T}}\)) is validated through smoke testing (‘Smoke testing and validation’) before heuristic generation begins, ensuring that \({\mathcal{H}}\) is always generated against a verified contract. The complete construction procedure is detailed in Supplementary Note 4.
- 
                  (1)
                  
                    Input designer: the input designer prompts the LLM to define the input schema \({\mathcal{I}}\), a typed dictionary specification that describes all problem data available to a heuristic at solve time (for example, distance matrix for the travelling salesman problem; job processing times and machine sequences for the job shop scheduling problem).
- 
                  (2)
                  
                    Output designer: the output designer prompts the LLM to define the output schema \({\mathcal{O}}\), a typed dictionary specification that describes the solution structure a heuristic must return (for example, a permutation of city indices for the travelling salesman problem; per-machine job sequences for the job shop scheduling problem).
- 
                  (3)
                  
                    Tool designer: the tool designer prompts the LLM to construct a library \({\mathcal{T}}=\{{\tau }_{1},{\tau }_{2},\ldots ,{\tau }_{K}\}\), where each tool τk is a callable Python function equipped with a name and a natural-language description, so that the heuristic generator can understand what each tool does and how to invoke it, following the paradigm of tool-augmented language models32,33. The tools serve two purposes: they inject problem-specific operational knowledge that may be absent from LLM pretraining corpora (for example, tugboat assignment feasibility rules in PSP), and they offload computationally intensive subroutines (for example, route cost calculation, 2-opt delta evaluation) so that heuristics remain lightweight decision rules. Among the tools, the feasibility checker is particularly important: rather than returning a binary verdict, it exposes the full step-by-step constraint validation process, allowing the LLM to read each constraint boundary explicitly and internalize it when designing heuristics, substantially reducing the generation of infeasible solutions.
- 
                  (4)
                  
                    Heuristic generator: given the constructed \(({\mathcal{I}},{\mathcal{O}},{\mathcal{T}})\), the heuristic generator issues n independent LLM calls to produce the initial portfolio \({{\mathcal{H}}}_{0}=\{{h}_{1},\ldots ,{h}_{n}\}\). Each call generates a single heuristic \(h:{\mathcal{I}}\to {\mathcal{O}}\) implemented as a self-contained solve function that reads an instance dict conforming to \({\mathcal{I}}\), invokes tools from \({\mathcal{T}}\) as needed and returns a solution dict conforming to \({\mathcal{O}}\). The free-form solve interface imposes no structural constraint on the algorithm’s internal logic, allowing heuristics to freely combine construction, local search and any other strategy within a single function. To promote diversity in \({{\mathcal{H}}}_{0}\), the generation prompt explicitly instructs the LLM to vary the underlying algorithmic paradigm (for example, greedy construction, simulated annealing, large neighbourhood search) across the n calls. All generated heuristics are subjected to smoke testing (‘Smoke testing and validation’) before being admitted to \({{\mathcal{H}}}_{0}\).
Stage two: heuristic evolution operators
Stage two generates new candidate heuristics through five LLM-based generation operators and two reactive repair operators (Algorithm 2). Each generation operator targets a specific limitation observed in instance-level performance of the current portfolio \({\mathcal{H}}\): insufficient exploitation, weak exploration, poor complementarity, limited diversity or premature convergence.
- 
                  (1)
                  
                    Local refinement (LR): Select a single heuristic \({h}_{{\mathrm{a}}}\in {\mathcal{H}}\) and generate \({h}^{{\prime} }=\,\text{LR}\,({{\mathrm{LLM}}},{P}_{{\rm{LR}}},{h}_{{\mathrm{a}}})\), where PLR is a prompt that instructs the LLM to apply a targeted local modification to one specific decision module of ha while preserving the rest. The parent is sampled according to: $$p(h)\propto \frac{1}{{\bar{r}}_{h}},\qquad {\bar{r}}_{h}=\frac{1}{m}\mathop{\sum }\limits_{i=1}^{m}{r}_{ih},$$(1) where rih ∈ {1,…, n} denotes the rank of heuristic h on instance i within the current portfolio \({\mathcal{H}}\) and \({\bar{r}}_{h}\) denotes the mean rank across all instances. This biases generation towards exploiting strong algorithms through incremental refinement.
- 
                  (2)
                  
                    Reflective redesign (RR): Select a single heuristic \({h}_{{\mathrm{a}}}\in {\mathcal{H}}\) and generate \({h}^{{\prime} }=\,\text{RR}\,({{\mathrm{LLM}}},{P}_{{\rm{RR}}},{h}_{{\mathrm{a}}})\), where PRR is a prompt that instructs the LLM to diagnose the structural weaknesses of ha and substantially rebuild its core logic. The parent is sampled according to: $$p(h)\propto {\bar{r}}_{h},$$(2) where a high \({\bar{r}}_{h}\) indicates consistently poor performance across instances. By targeting weak algorithms for transformative redesign, RR unlocks new search directions that incremental refinement cannot reach.
- 
                  (3)
                  
                    Complementary crossover (CC): Select a pair \(({h}_{{\mathrm{a}}},{h}_{{\mathrm{b}}})\in {\mathcal{H}}\) and generate \({h}^{{\prime} }=\,\text{CC}\,({{\mathrm{LLM}}},{P}_{{\rm{CC}}},{h}_{{\mathrm{a}}},{h}_{{\mathrm{b}}})\), where PCC is a prompt that instructs the LLM to synthesize a dispatcher-style heuristic that adopts ha’s strategy when ha is strong and hb’s strategy when hb is strong. The pair is sampled with probability proportional to their complementarity score: $$p(\{{h}_{{\mathrm{a}}},{h}_{{\mathrm{b}}}\})\propto C({h}_{{\mathrm{a}}},{h}_{{\mathrm{b}}})=\frac{1}{m}\mathop{\sum }\limits_{i=1}^{m}| {r}_{i{\mathrm{a}}}-{r}_{i{\mathrm{b}}}| ,$$(3) which prefers pairs that disagree most on which instances they handle well, ensuring the synthesized heuristic bridges two genuinely complementary specialists.
- 
                  (4)
                  
                    Comparative synthesis (CS): Select a pair \(({h}_{{\mathrm{a}}},{h}_{{\mathrm{b}}})\in {\mathcal{H}}\) and generate \({h}^{{\prime} }=\,\text{CS}\,({{\mathrm{LLM}}},{P}_{{\rm{CS}}},{h}_{{\mathrm{a}}},{h}_{{\mathrm{b}}})\), where PCS is a prompt that instructs the LLM to diagnose the performance contrast between a strong and a weak algorithm and distil the winning decisions into a new heuristic. The two parents are sampled independently according to: $$p({h}_{{\mathrm{a}}})\propto \frac{1}{{\bar{r}}_{{h}_{{\mathrm{a}}}}},\qquad p({h}_{{\mathrm{b}}})\propto {\bar{r}}_{{h}_{{\mathrm{b}}}},\quad {h}_{{\mathrm{b}}}\in {\mathcal{H}}\setminus \{{h}_{{\mathrm{a}}}\},$$(4) where ha is drawn to prefer strong algorithms and hb is drawn from the remaining portfolio to prefer weak algorithms. By explicitly contrasting what the winner does differently from the loser, CS extracts actionable design principles that are difficult to discover through local refinement alone.
- 
                  (5)
                  
                    Diversity injection (DI): Take the existing portfolio \({\mathcal{H}}\) as input and generate \({h}^{{\prime} }=\,\text{DI}\,({{\mathrm{LLM}}},{P}_{{\rm{DI}}},{\mathcal{H}})\), where PDI is a prompt that instructs the LLM to identify common decision patterns shared across all members of \({\mathcal{H}}\) and construct a new heuristic whose core logic differs along as many dimensions as possible. This operator targets logical blind spots of the current portfolio, mitigating premature convergence to a narrow algorithmic family.
- 
                  (6)
                  
                    Error repair (ER): When a candidate heuristic h′ fails execution (for example, syntax error or infeasible output), ER is applied as a reactive operator: \({h}^{{\prime} }\leftarrow \,\text{ER}\,({{\mathrm{LLM}}},{P}_{{\rm{ER}}},{h}^{{\prime} },\varepsilon )\), where ε is the error message or infeasibility report and PER instructs the LLM to patch the smallest possible region of the code without altering the core algorithmic logic. The repair cycle repeats up to Nrep attempts; candidates that remain invalid are discarded.
- 
                  (7)
                  
                    Efficiency improvement (EI): When a candidate heuristic h′ exceeds the prescribed runtime budget Tmax on any instance, EI is applied as a reactive operator: \({h}^{{\prime} }\leftarrow \,\text{EI}\,({{\mathrm{LLM}}},{P}_{{\rm{EI}}},{h}^{{\prime} })\), where PEI instructs the LLM to reduce computational complexity (for example, replacing O(n2) loops with greedy approximations, caching repeated computations) while preserving the core decision logic. The repair cycle repeats up to Neff attempts; candidates that remain over-budget are discarded.
During each evolution iteration, one of the five generation operators (LR, RR, CC, CS or DI) is selected uniformly at random, and ER and EI are applied reactively as needed. This uniform sampling ensures that no single improvement direction dominates the search, maintaining portfolio diversity throughout evolution.

Smoke testing and validation
LLM-generated code may contain syntax errors, runtime exceptions or produce infeasible outputs20. To ensure code reliability, LACE employs a lightweight smoke test that validates both the problem contract (\({\mathcal{I}}\), \({\mathcal{O}}\), \({\mathcal{T}}\)) at the end of stage one and each candidate heuristic during stage two. Each component is executed on a small set of validation instances designed to verify functional correctness; it passes if it runs without errors and produces output conforming to the expected schema. When validation fails, the error message is passed to ER, which attempts to patch the code while preserving the core logic. The repair cycle repeats up to Nrep attempts; components that remain invalid after all attempts are discarded and regenerated.
Experimental settings and implementation details
We evaluate LACE on 40 CO problems: 36 problems from CO-Bench30, which we report under five problem families (scheduling; routing and graphs; packing and cutting; location and assignment; and selection and knapsack), plus four new problems treated as a sixth family (PSP, TRS, MB-TRS and TRS-VS; mathematical formulations and instance-generation procedures are provided in Supplementary Notes 1 and 2). For each problem, the development instance set \({\mathcal{D}}\) consists of m = 128 instances drawn from the CO-Bench or the corresponding new-problem generator; the held-out test sets contain 7,109 instances in total across the 40 problems (average of 178 instances per problem). For the 36 CO-Bench problems, \({f}_{p}^{\;* }\) is the per-instance best-known objective reported in existing studies. For the four new problems, no published optimum exists, so \({f}_{p}^{\;* }\) is set to the best objective achieved by any method compared in Fig. 3 in that instance. For Fig. 2, baseline scores marked with ‘a’ in the figure caption are taken directly from CO-Bench30; we evaluated all other methods (including LACE) under the same CO-Bench protocol.
LACE is run with portfolio size n = 10 and Nmax = 6 evolution iterations, producing 70 candidate heuristics per problem (an initial portfolio of 10 plus 60 generated during evolution), closely matching the 64-candidate generation budget used by the LLM-based baselines in CO-Bench. Reactive operators allow Nrep = 3 repair attempts on execution failures (ER) and Neff = 3 efficiency-improvement attempts on runtime violations (EI); candidates that remain invalid or over-budget after these attempts are discarded. The per-instance runtime budget Tmax is set to 10 s for CO-Bench problems (matching the CO-Bench protocol) and 60 s for the four new problems (reflecting the larger instance sizes). The complementary selection step solves the MILP using Gurobi 11.0. All LLM calls are routed through the OpenRouter API. The framework, the problem contracts and the metaheuristic baselines are implemented in Python 3.10 and rely on NumPy 1.24, SciPy 1.10, NetworkX 3.0, python-mip 1.15 and the OpenAI Python client 1.0 for API access; figures were produced with Matplotlib 3.8. The exact dependency specification is released with the code. The default backbone is OpenAI o3 Mini at reasoning effort medium; as it is a reasoning model, decoding sampling parameters are not user-configurable. The other three backbones evaluated in Fig. 5 (DeepSeek V4 Pro, Claude Sonnet 4.6 and Gemini 3 Flash Preview) use temperature 0.7 and top-p 0.95. Constructing the problem contract is a one-time step per problem, separate from the search: measured end to end with the released contract generator, its token cost for a full helper library is minor relative to the search itself (about 2–5% of the average per-problem token usage reported in Fig. 5a), and this cost does not grow with the evolution budget. At deployment, the portfolio heuristics are executed independently, one central processing unit core each, under the same per-instance wall-clock limit as every baseline; the reported score is the best feasible objective across the portfolio per instance, selected using only each solver’s self-computed objective value, and no LLM is invoked at test time.
Six metaheuristic baselines (Fig. 3) were implemented in Python and tuned per problem on a development set; implementation details and hyperparameters are reported in Supplementary Note 3 and Supplementary Table 3. Stochasticity is evaluated on the four new problems (Fig. 3), where each method is run for five independent random seeds and box plots show the distribution across runs; the remaining experiments (Figs. 2, 4 and 5) report a single LACE run per configuration. On the default OpenAI o3 Mini backbone, the full 40-problem LACE run consumes approximately 154M tokens and US$368 in API charges in aggregate, with mean per-problem wall-clock time of 59 min. All experiments ran on compute nodes, each with two Intel Xeon 8375C central processing units (64 cores/128 threads total) and 512 GB RAM. Within each node, candidate heuristics are evaluated in parallel across the 128 development instances; across the 40 problems, LACE runs independently in parallel on separate nodes, as no inter-problem coordination is required. LLM calls are issued sequentially through the OpenRouter API.
